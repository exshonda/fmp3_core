○本ドキュメントについて

本ドキュメントはARM64コア依存部の設計メモである．現状はARM64の仕様，
GICの仕様も含むが将来的には分離する予定である．

ARM64の仕様は膨大であるため，カーネルの実装に関連する事項についてのみ
記載する．

○割込み関連の設計

●割込みに関するATFの仕様（SW）

BL32(FMP)を実行する際には，SCR_EL3.FIQを0，SCR_EL3.IRQを0，例外レベル
をEL1とする．そのため，各割込み発生時の受け付け例外レベルは次のように
なる．

・IRQ : S-EL1
・FIQ : S-EL1

Non-Secureカーネルを実行する際には，SCR_EL3.FIQを1，SCR_EL3.IRQを0，例
外レベルをEL1とする．そのため，各割込み発生時の受け付け例外レベルは次
のように

・IRQ : NS-EL1
・FIQ : S-EL1


●S/NSにおける優先度の扱い（HW）

【GICv3/4】SCR_EL3.FIQが1であるため，各レジスタへのNSからのアクセスは
次のようになる．

ICC_PMR_EL1/ICC_RPR_EL1
・内容が0x00-0x7F
  ・0x00が読み込め，ICC_PMR_EL1へ書き込み出来ない
・0x80-0xFF
  ・優先度のNS読み書き時のルールが適用される
  
GICx_IPRIORITYR<n>:
  ・優先度のNS読み書き時のルールが適用される
  
【GICv2】SCR_EL3.FIQの設定値に関わらず，上記のルールが適用される．

        
●【GICv3/4】【GICv2】NS読み書き時のルール（HW）

NSG1の割込みに対して適用される．

NSで優先度を読み込むと実際の優先度を1ビット左シフトした値が読み込める．

NSで優先度を書き込むと優先度を1ビット右シフトして上位ビットに'1'を設定
した値が書き込まれる．

これより，NSが扱う優先度は，物理的な優先度の下半分にマッピングされる．
詳細は文献[1]Figure 3-7及び文献[2]Figure 4-9を参照のこと．

例)8bitの場合
 NS視点の優先度範囲 0x00～0xFE
 物理的な優先度範囲 0x80～0xFF


●【GICv3/4】【GICv2】割込みグループ（HW）

【GICv2】

グループ0(G0INT)とグループ1(G1INT)に設定可能．

●F/Iフラグについて(HW)

ARMv8-Aでは，FフラグとIフラグは同一のステータスレジスタ中で保持される
ではなく，独立したフラグとして扱われる．

F/Iフラグにアクセスする方法は次の二種類がある．ビットの定義が異なるた
め注意が必要である．

・他のフラグ共に読み込み書き込み．
 - 読み込み : mrs \reg daif
 - 書き込み : msr daif \reg
 ・ビット定義
     FIQ : 0x040
     IRQ : 0x080
          
・個別セット・クリア
 - セット : msr DAIFSet, #imm
 - クリア : msr DAIFClr, #imm
 ・imm の値
    FIQ : 0x001
    IRQ : 0x002

TrustZoneあり(S)の場合，別案として タスク実行時の割込み優先度マスクを
0xFFとし，【GICv2】では常にIフラグをセットし，【GICv3/4】ではFフラグを
マスクする方法がある．こちらの方法は上記の手法と比較して次のデメリット

・I/Fフラグの設定を誤るとNon-Secure側の割込みが受け付けられる．
  OS実行中はI/Fフラグの変更は頻繁に行うためバグの原因となる．一方，PMR

・条件フラグが減らせる
  【GICv3/4】ではTrustZoneなしと比較して，I/Fフラグの扱いに変更がない．
  【GICv1】でも常にセットしないといけないフラグがない．
    
・G1INTを使用出来ない【GICv3】
  将来的にカーネル管理外割込みを使用したい場合に，G1INTを使用すること
  が出来ない．

================================================================
GIC Redistributor ベースアドレスの扱い（gicr_base 配列の廃止）
================================================================

■ 概要
各PEの GIC Redistributor フレーム先頭アドレスを，共有可変配列 gicr_base[]
に保存する方式から，マクロ GICR_BASE_ADDR(x) で毎回計算する方式へ変更した．

  gic_kernel_impl.h:
    #define GICR_BASE_ADDR(x)  (GICR_BASE + GICR_SIZE * (uintptr_t)(x))
    #define GICR_xxx(x)        (GICR_BASE_ADDR(x) + ... )

  gic_kernel_impl.c: gicr_base[] 配列定義と gicr_init() 内の代入を削除．

■ 変更理由（不具合の根絶）
Redistributor 先頭は「GICR_BASE + GICR_SIZE × PEインデックス」の固定スト
ライドで一意に決まる純粋な計算式であり，全 arm64 ターゲットの gicr_init()
が元々この式で gicr_base[] を初期化していた．すなわち配列は計算結果の
キャッシュにすぎない．

ところがこの配列は次の理由で危険であった：
 ・各PEが gicr_init() で gicr_base[自PE] を「データキャッシュON」で書く．
 ・一方 per-PE の L1 ページテーブル（arm64.c の tt_pri）は，オーナPEが
   mmu_init() で「キャッシュOFF」のまま DRAM へ直接書く．
 ・両者がリンカ配置で同一キャッシュライン上に隣接すると，あるPEの
   gicr_base 書込みでキャッシュに載ったライン（古いページテーブル値を
   含む）が writeback され，他PEがキャッシュOFFで書いた有効なテーブル
   エントリを DRAM 上で上書きする（false sharing）．結果，MMU walk で
   未マップ例外を起こす（SMP 4コアで顕在化）．

従来はこれを「gicr_base[] をキャッシュライン境界に整列してページテーブル
と別ラインに分離する」対症療法で回避していた．本変更では配列そのものを
廃止し，共有書込み先を無くすことで不具合を根本から除去する（計算は配列
ロードより軽量でもある）．

■ 配列ごとの整列は新たに必要にならないか（検討）
不要である．false sharing の一方の当事者（キャッシュONで書かれる
gicr_base）が消えるため，キャッシュOFFで書かれるページテーブル側に新た
な整列を追加する必要はない．ページテーブル配列 tt_pri は

  static uintptr_t tt_pri_prcN[TT_FIRST_ENTRY_NUM]
                     __attribute__((aligned(TT_FIRST_SIZE)));

であり，TT_FIRST_SIZE は arm64.h で下限 64（= ARM64_CACHELINE_SIZE = キャッシュ
ライン長）が保証されている（(TT_ENTRY_SIZE*TT_FIRST_ENTRY_NUM) が 64 以下
なら 64 に切り上げ）．よって各 tt_pri はキャッシュライン境界に整列し，かつ
サイズもライン長の整数倍となるため，他のどの変数とも同一ラインを共有し
ない（自己隔離）．他のキャッシュON書込み変数が隣接しても安全である．

■ 前提条件
Redistributor が「GICR_BASE から GICR_SIZE 刻みで連続配置」であること．
GICv3/4 で再分配器が不連続配置の SoC では本式は使えず，GICR_TYPER の
アフィニティ照合による探索が必要になる（その場合は別途実装する）．i.MX95
を含む現行 arm64 ターゲットはいずれも固定ストライドであり問題ない．


================================================================
TTSP3 ソフト制御クロックと cval_shared（MP専用）の扱い
================================================================

■ TOPPERS_RUN_TTSP3 について
ARM64 のコア内蔵タイマ(Generic Timer)はカウンタを停止できないため，TTSP3
の決定論的テストでは時刻を凍結・制御する必要がある．そこで TTSP3 ビルド時
(TOPPERS_RUN_TTSP3 定義時)のみ，ソフト制御クロック(stop_tick / gain_tick)で時刻
を進める方式を core_timer.h/.c に用意している．TOPPERS_RUN_TTSP3 は ARM64 共通の
仕組みであり，各ターゲットの ttsp_target.sh の CONFIG_OPT が -DTOPPERS_RUN_TTSP3
を付与する（本番ビルドでは未定義＝当該コードは全てコンパイル対象外）．
TTSP3 ターゲットを持たないターゲット(zynqmp, stm32mp2, agilex5soc 等)には
一切影響しない．

■ cval_shared は MP(2コア以上)専用
stop_tick 中はコンパレータ割込みがマスクされるため，タイムイベントの発火は
gain_tick が肩代わりする．単一PE では gain_tick が自PEのコンパレータを見て
発火させれば足りるが，MP では他PEのコンパレータも発火させる必要がある．その
ために各PEがコンパレータ値を共有配列 cval_shared[] に保存し，タイムマスタPE
の gain_tick がこれを走査して cross-PE に割込みを pending する．

cval_shared[] の実体は各ターゲットの ttsp_target_test.c が定義する（soft-clock
変数 stop_tick/stop_time/temp_gtc/tick_int と同じ流儀）．MP 非対応の TTSP3
ターゲット(例: imx8mm は PROCESSOR_NUM=1 の単一PE TTSP)の ttsp_target_test.c
は cval_shared[] を定義しない．

■ 共通部での参照を TNUM_PRCID >= 2 でガードする理由
共通 core_timer.h が TOPPERS_RUN_TTSP3 だけで無条件に cval_shared[] を参照すると，
cval_shared[] を定義しない単一PE TTSP3 ターゲット(imx8mm 等)のビルドが未定義
シンボルでリンクできなくなる．cval_shared は本来 MP 専用機構なので，参照を

  #if defined(TOPPERS_RUN_TTSP3) && (TNUM_PRCID >= 2)

でガードする（宣言・set_cval・clear_event の3箇所）．これにより
 ・単一PE TTSP3 (TNUM_PRCID==1, 例 imx8mm) : cval_shared を参照せずビルド可
 ・MP TTSP3 (TNUM_PRCID>=2, 例 imx93/imx95): 従来どおり cross-PE 発火が機能
となり，意味的にも(MP専用機構を MP のときだけ使う)正しい．

i.MX9 ファミリのチップ依存部共有（imx9/）
================================================================

■ 背景
i.MX93 と i.MX95 のチップ依存部(arch/arm64_gcc/imx93, imx95)はロジックが
完全に同一で，差は SoC 固有の定数(GICR_BASE 等)とコア数(TNUM_PRCID)，名前/
文書だけであった．重複保守(片方更新し忘れ)を避けるため共通化した．

■ 構成
  arch/arm64_gcc/imx9/        ← i.MX9 ファミリ共通の実体(1つ)
     chip_kernel_impl.c, chip_serial.c, lpuart.c,
     chip_kernel.h, chip_kernel_impl.h, chip_serial.h, chip_stddef.h,
     chip_timer.h, lpuart.h, chip_kernel.trb, chip_serial.cfg,
     chip_timer.cfg, chip_rename.def, chip_rename.h, chip_unrename.h,
     Makefile.chip(共通ロジック)
  arch/arm64_gcc/imx95/       ← SoC 固有(薄い)
     imx95.h(GICR_BASE 等の #define), imx9_soc.h(= #include "imx95.h" の1行),
     Makefile.chip(= imx9/Makefile.chip を include するだけ),
     chip_user.txt, MANIFEST
  arch/arm64_gcc/imx93/       ← 同様(imx93.h)

■ #if を使わない SoC 切り分け
共通コードは SoC ヘッダを実名でなく汎用名 "imx9_soc.h" で include する．
imx9_soc.h は各 SoC dir にあり，その SoC の imx9x.h を取り込む 1 行 shim．
ビルド時にどの SoC dir が include パスに載るかで切り替わる(下記)．共通コード
内に #if 分岐は無い．チップ略称マクロ TOPPERS_IMX9x も chip_stddef.h(共通)
から imx9x.h(per-SoC)へ移した(未使用マーカーだが SoC 別に保持)．

■ ビルド配線
Makefile.target の CHIP(=imx95 等) で arch/arm64_gcc/$(CHIP)/Makefile.chip を
include する仕組みは不変．per-SoC の Makefile.chip は imx9/Makefile.chip を
include するだけ．imx9/Makefile.chip が
  CHIPDIR = arch/arm64_gcc/$(CHIP)   (SoC固有: imx9_soc.h, imx9x.h)
  IMX9DIR = arch/arm64_gcc/imx9       (共通実体)
の両方を INCLUDES/KERNEL_DIRS/SYSSVC_DIRS に追加する．共通 .c は IMX9DIR から
コンパイルされ，SoC ヘッダは CHIPDIR から解決される．

■ 検証
imx95(6コア): ビルド＋実機6コア起動確認済．imx93(2コア): ビルド確認済
(実機確認は後日)．新規 SoC を足す場合は arch/arm64_gcc/<soc>/ に imx9x.h ＋
imx9_soc.h ＋ 薄い Makefile.chip ＋ target を用意するだけでよい．
