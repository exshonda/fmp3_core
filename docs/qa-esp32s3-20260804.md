## R-2【最優先・方針確認】自己削除した動的タスクの資源回収 → **(i) 移植側回収の前提**

**カーネル側で `ext_tsk` 時に解放する意図・予定は無い。** 理由は3つ:

1. **dcre 忠実移植の原則**: dcre 自身が ext_tsk で資源を解放しない。回収経路は
   `del_tsk`（他タスク文脈・休止状態必須）のみ。
2. **設計として不可能側に倒してある**: ext_tsk 内での自スタック解放は「自分がまだ
   実行中のスタック」の解放になる。段階1 spec §2.3 に記録した受容済みウィンドウ
   （ext_tsk は release_glock 後も自スタック上で数命令実行する — pristine 継承）が
   既にあり、ext_tsk 内解放はこの窓を「理論上」から「必然」へ広げるため採らない。
3. `del_tsk` の休止必須制約により**自己回収は構造的に不能**（走行中の自分は休止でない）。

貴側の読解（`task_term.c` 差分は TA_NOEXS ガード追加のみ）は**正確**。

**推奨回収パターン**（本リポジトリで QEMU 実証済み）:
`get_tst` で `TTS_DMT` をポーリング → `del_tsk`（`test/test_dcre1.c` シナリオ8。
del_tsk は休止なら任意コアから可能）。reaper でも次回 create 時掃除でも可。

★**設計判断に効く追加情報 — プールは bump アロケータ**（`docs/dynamic-creation.md` §6）:
`free_mpk`（del_tsk 経由）は**割当カウントを減らすだけで brk は戻らない**。
brk が先頭へ戻るのは**カウントが 0（全割当解放）になった瞬間だけ**。
つまり **reaper で回収しても、プール上に他の生存割当（他タスクのスタック・
dtq/pdq/mpf の TA_MBALLOC 管理領域）が 1 つでも残る限り、create/self-delete の
反復でアリーナは単調に痩せ続ける**。回避策の候補:
- **ユーザ供給スタック**（`T_CTSK.stk != NULL`）にする — プールを一切使わず
  TA_MEMALLOC も立たない。貴側の既存静的スロット配列をスタック供給源に転用すれば、
  帳簿は残るがプール劣化は消える（reaper も不要になる可能性がある）
- または「世代」単位で全動的オブジェクトを同時に解放するアプリ設計（count==0 を作る）

## R-1【情報】arch 依存関数の一覧 → **必須は USE_TSKINICTXB 時の2関数のみ。他オブジェクトはゼロ**

- **タスク**: `USE_TSKINICTXB` を定義する arch のみ、`init_tskinictxb(TSKINICTXB*, size_t, STK_T*)`
  と `void *tskinictxb_memalloc_ptr(TSKINICTXB*)` の2つが必要。貴側の対処
  （esp32_s3 `9e2ada9`）と規約実測（stk_top=先頭/stk_bottom=先頭+サイズ）は**正しい**。
  なお acre_tsk は `stksz = ROUND_STK_T(stksz)` 後に init_tskinictxb を呼ぶため
  （`kernel/task_manage.c:194-197`）、静的側の `ROUND_STK_T` 済みサイズと規約一致する。
  ※`USE_TSKINICTXB` を使わない arch（riscv 等 — TINIB が stksz/stk を直接持つ）は
  何も不要。
- **sem/flg/mtx/dtq/pdq/mpf**: arch 依存関数の新規要求**なし**（カーネル層で完結）。
- **cyc/alm**: 新規関数なし。既存の `TOPPERS_TEPP_PRC`（target_kernel.h）を参照するのみ
  （静的生成でも必要な既存マクロ。動的 cyc/alm の affinity に使う）。
- **ISR（ENA_DYNISR）**: arch 関数の新規要求**なし**。結合は既存の
  `INT_ENTRY`/`INTHDR_ENTRY` マクロ経由のみ（R-3 参照）。
- **フォールバック群**（arch が定義していればそれが優先・未定義なら kernel 側の
  `#ifndef` 既定が効く）: `TARGET_TSKATR`・`TARGET_MIN_STKSZ`（`kernel/kernel_impl.h`）、
  `CHECK_*_ALIGN`/`CHECK_FUNC_NONNULL` 系（`kernel/check.h` — 未定義なら検査が
  恒真に落ちる。Xtensa で厳密化したければ arch 側で定義）。

恒久文書化: `docs/dynamic-creation.md` に**「移植者向け: arch 層の要件」節を追加した**
（本回答と同じコミット）。以後はそちらが正本。

## R-3【制約】Xtensa の結合点2つ → **両方とも保つ。確約する**

1. **`_kernel_inthdr_N` のシグネチャは `void(void)` のまま**（queue-mode でも）。
   現物: `build/kria_r5-2core-tmixma/generated/kernel_cfg.c:262` に
   `void _kernel_inthdr_40(void)` — 中身が `_kernel_call_isr(&_kernel_isr_queue_table[i]);`
   の1行になるだけで、`INT_ENTRY`/`INTHDR_ENTRY` の使用経路・受け渡しは不変。
2. **`INTINIB`（5要素）・`INHINIB`（4要素）の構造・生成は一切変えていない**。
   変える予定も無い。将来変えるときは事前に連絡する。

★**補足への重要な先回り回答（段0測定で必ず見えるもの）**:
「ENA_DYNISR 無効時に生成物が変わらない」は**ディスパッチコードについては保証**
（test_int2 の inthdr バイト不変で実証済み）だが、**kernel_cfg.c 全体のバイト不変では
ない**。AID 系の**恒常出力**（設計裁定・各 spec の「管理された差分」）が、静的オブジェクト
を持つ全構成に出る。段0 で見える追加シンボルの類型:
- 全オブジェクト共通: `TNUM_S*ID` 定義・`_kernel_tmax_s*id`・inib/torder のサイズ
  トークン変更・`TOPPERS_EMPTY_LABEL(*INIB, _kernel_a*inib_table)` 群
- mpk: `_kernel_mpksz = 0` / `_kernel_mpk = NULL`
- ISR（CRE_ISR を1個でも持つ構成 — 貴側は該当）: `_kernel_isrinib_table` /
  `_kernel_isrcb_*` / `_kernel_p_isrcb_table` / `_kernel_isrorder_table` /
  `_kernel_tmax_isrid` 系 / EMPTY_LABEL 群 / 起動時 `_kernel_initialize_isr` 呼出し
- 実測 ROM 影響（musca_b1 sample1）: text +1796 / data +0 / bss +72 バイト

**追加シンボルはすべて `_kernel_` プレフィクスのカーネル帰属**であり、シム／アプリ由来
シンボルの変化は無いはず。貴側のシンボル単位帰属の判定なら「カーネル帰属の追加のみ・
既存シンボルの変化なし」が期待値。もしシム/アプリ帰属の変化が観測されたら、それは
こちらでも説明できない事象なので改めて照会してほしい。
- `DEF_INH` 9本との関係: **ENA_DYNISR を書かない限り一切不変**。同一 intno に
  DEF_INH がある intno への ENA_DYNISR は cfg エラー（E_OBJ）で拒否される。

## R-4【確認】→ **貴側の理解は正確。自衛策も的確**

- `TNUM_PRCID == 1` での `mact_tsk(id, 2)` は **E_ID で正しい**
  （現物確認: `kernel/task_manage.c:384` の `CHECK_PRCID` が `:386` の `CHECK_MIG` に
  先行し、`kernel/check.h:340-342` が E_ID を返す）。
- 補足: deferred 項目の対象は「**一度も acre されていないスロット ID の捏造**」のみ。
  acre → del 済み ID への `mact_tsk` は **E_NOEXS が正しく返る**（E_NOEXS ゲートは
  実装・テスト済み）。「acre_tsk が成功して返した ID にしか撃たない」という貴側の
  不変条件で完全にカバーされる。
