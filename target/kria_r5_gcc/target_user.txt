１．ZynqMP_R5ターゲット依存部の概要

KRIA_R5ターゲット依存部（GNU開発環境向け）は，TOPPERS/FMP3カーネルを，
AMD（Xilinx）社のKria SOMファミリ（Zynq UltraScale+ MPSoC）のRPU
（Cortex-R5F）上で動作させる環境を構築するためのものである．シングルコア
（lockstep相当，TNUM_PRCID=1）と，split modeによる2コアSMP（TNUM_PRCID=2）
の両構成をサポートする．対応ボードは KR260／KV260（K26 SOM），KD240
（K24 SOM）で，RPU（Cortex-R5F）は全Kriaで同一である．ボード差はmake変数
BOARD=kr260|kv260|kd240 で起動バナー名のみ切替える（既定kr260，不正値は
$(error)）．チップ依存部（arch/arm_gcc/zynqmp_r5）は zcu102_r5_gcc と共用
する（同一SoC）．

実行環境はアップストリームQEMU（バージョン11以降のqemu-system-aarch64）
および実機（Kria）である．QEMUで実行する場合には，TTCの駆動周波数を133MHz
に設定する必要がある（Makefile.targetのQEMU変数＝デフォルトtrueで自動設定
される．実機向けはmake QEMU=false で100MHz化）．

1.1 対応するターゲットシステムとターゲット略称

QEMUおよび実機（Kria）で動作確認を行っている．

	QEMU: アップストリーム qemu-system-aarch64 version 11.0.0
		（マシン xlnx-zcu102を流用．システム付属の8.2.2はRPU用GIC
		未実装のため使用できない）．2コアSMPはRPU用GICのバンクマップ
		等を修正したQEMUビルドが必要（5.制限事項参照）．
	実機: KV260／KR260 にて JTAG（xsct，split mode，make QEMU=false）で
		2コアSMP起動を確認（Step12）．cross-PRCアラーム（malarm1）・
		spinlock1 を含むMPテストの実機PASSを確認済み．

ターゲット略称等は次の通り．

	ターゲット略称：kria_r5_gcc
	システム略称：zynqmp_r5
	開発環境略称：gcc

1.2 ターゲット依存部の構成

	target/
		kria_r5_gcc/			KRIA_R5ターゲット依存部

	arch/
		arm_gcc/common/			ARMコア依存部
		arm_gcc/zynqmp_r5/		ZynqMP RPUチップ依存部
		gcc/					GCC開発環境依存部

タイマ・シリアル等の実装はチップ依存部にある．「ZynqMP RPUチップ依存部
ユーザーズマニュアル」（arch/arm_gcc/zynqmp_r5/chip_user.txt）を併せて
参照すること．

1.3 開発環境と動作確認条件

GNU ARM Embedded Toolchain（arm-none-eabi）を用いる．動作確認を行った
バージョンは次の通り．

	gcc: 13.2.1（Ubuntuパッケージ）
	ruby: 3.2.3（コンフィギュレータ）

FPU設定はUSE_ARM_FPU_ALWAYS＋vfpv3-d16（hard float）である．

1.4 メモリマップ

	0x00000000 - ：ベクタテーブル（.vector）
	0x7f000000 - ：コード・データ（.text等）

Cortex-R5はVBARを持たないため，例外ベクタは0番地に固定である（SCTLR.V=0
で使用）．メモリ配置はリンカスクリプト（kria_r5.ld）で定義しており，
変更する場合は同ファイルを修正する．TCM（QEMU未モデル）・OCM（MPU無効時
のXN制約）は使用しない．


２．ターゲット定義事項の規定

割込み番号・割込み優先度・CPU例外ハンドラ番号・クラス（CLS_PRC1等）は，
チップ依存部マニュアルを参照すること．


３．ドライバ関連の情報

高分解能タイマ（TTC3カウンタ0）とシリアル（非TECS: chip_serial＋
xuartps）はチップ依存部で実現している．

サンプルプログラムのポート1をUART1（0xFF010000，QEMUでは2番目の
-serial）に，ポート2をUART0に対応させている．システムログの低レベル出力
はポート1（UART1）へのポーリング出力である．


４．システム構築手順と実行手順

4.1 システム構築

FMP3 3.4.0はtecsgen非同梱のため，非TECS構成（-w）でビルドする．非TECS時
のsyssvc実装とSIOドライバはMakefileに自動では入らないため，-Sで明示する．

	% cd fmp3_trunk/obj
	% mkdir obj_kria_r5 && cd obj_kria_r5
	% ruby ../../configure.rb -T kria_r5_gcc -w \
		-S "syslog.o serial.o serial_cfg.o logtask.o banner.o \
			chip_serial.o xuartps.o"
	% make BOARD=kr260			… QEMU向け（TTC=133MHz，既定kr260）
	% make BOARD=kv260 QEMU=false	… 実機向け（TTC=100MHz）

ボード差は make 変数 BOARD=kr260|kv260|kd240 による起動バナー名のみで，
機能差はない（既定 kr260）．2コアSMP（TNUM_PRCID=2）で構築する場合，QEMU
での2コア実行はRPU用GICのバンクマップを修正したQEMUビルドが必要である
（5.制限事項）．実機（Kria）では make QEMU=false でビルドする．

なお，arm-none-eabi gcc 14系では，チップ層 chip_kernel_impl.c の
mpu_set_region／mpu_disable_allregion がプロトタイプ宣言を持つよう恒久
修正済みであり，回避フラグなしでビルドできる．

4.2 QEMUでの実行方法

	% qemu-system-aarch64 -M xlnx-zcu102 -smp 6 -m 2G -nographic \
		-global xlnx-zynqmp.boot-cpu=rpu-cpu[0] \
		-global cortex-r5f-arm-cpu.mp-affinity=0 \
		-device loader,file=fmp,cpu-num=4 \
		-serial null -serial mon:stdio

ビルドディレクトリではmake経由でも実行できる．

	QEMUでの実行：            make runqu QEMU_UPSTREAM=<qemuのパス>
	QEMUをデバッグ待ちで起動：make runqug QEMU_UPSTREAM=<qemuのパス>

4.3 デバッガの使用方法

QEMUを-s -S付き（make runqug）で起動し，gdb-multiarchから接続する．
RPUクラスタは別inferiorである点に注意．

	(gdb) target extended-remote :1234
	(gdb) add-inferior
	(gdb) inferior 2
	(gdb) attach 2
	(gdb) file fmp


５．制限事項

	・QEMUでの2コアSMP（split動作）は，システム付属のQEMUでは動作しない．
	  RPU1用のGIC CPUインタフェースが正しくバンクマップされないため，
	  当該箇所等を修正したアップストリームQEMUビルドが必要である（実機
	  では本制約はなく，2コアSMPが動作する．Step12で確認済み）
	・QEMUでは spinlock1 が NOOUT になる（TCG単一スレッドのスケジューリング
	  による假象．実機では並列動作のためPASS）
	・メモリ保護なし（保護が必要な場合はHRP3版を使用すること）

	【Kria実機運用上の注意】KriaはJTAGブートモード非対応で，電源投入で必ず
	QSPI/SDのboot.bin（FSBL→BL31→U-Boot）が走る．rst -system／psu_init／
	reset_apu はQSPI再ブートおよびDDR破壊を招くため使用してはならない．
	FSBL初期化済みのDDRに対し，RPUをsplitにして使用コアを rst -processor
	（DDR保持）後に dow してから con で起動する．また，クリーンなU-Boot起動
	状態にしてからJTAGロードすること．

	【最重要・NOOUTの最頻原因】起動するR5コア数は，必ずバイナリの TNUM_PRCID
	（＝ビルド時の PRC_NUM，R5既定は 1）と一致させること．barrier_sync は起動
	時に TNUM_PRCID 個の全プロセッサがバリアに到達するまでマスタ（R5#0）を待た
	せ，このバリア到達はバナー出力よりも前に行われる．したがって起動コア数が
	TNUM_PRCID より少ないと，マスタがバリアで永久待ちとなり，バナーが1文字も
	出力されず「コンソール無反応（NOOUT）」に見える．これはボード／UART／JTAG
	の故障ではなく，起動コア数の不足である（arm64版 kria_arm64_gcc の A53 と
	同根．実機で確認）．sample1 等 PRC_NUM 未指定のビルドは既定 TNUM_PRCID=1
	のため「1コア（R5#0のみ）」で起動する．MP系は PRC_NUM=2 で「2コア起動」．

	【make による実機実行・コンソール】上記手順は Makefile.target の make ルール
	にまとめてある．ビルドディレクトリ（<OBJ>）で，別端末で2つに分けて使う
	（xsct/hw_server には Vitis の bin へ PATH を通しておくこと）．
	  make console  UART1 コンソール（carrier card の USB シリアル intf=01）を
	                自動検出して開く（picocom/cu 自動選択．TTY=... で明示可）．
	  make run      hw_server（未起動なら自動起動）へ attach し，RPU split で
	                NCORES 個の R5 を起動する．★NCORES は PRC_NUM から自動導出
	                （未指定時は 1）されるため，起動コア数と TNUM_PRCID の不一致
	                （上記NOOUT原因）を防げる．
	  make hwserver hw_server を前面起動（通常は run が自動起動するので不要）．
	使用スクリプト:
	  tools/jtag/jtag_r5_kria_attach.tcl  （常駐 hw_server へ attach・ncores 可変）
	  tools/jtag/jtag_r5_2core_kria.tcl   （2コア固定・従来版）
	※ R5 と A53(APU) は同じ PS UART1 を共有するため，A53側で別カーネルが走って
	  いるとコンソールが混信する．クリーンなU-Boot起動状態で使うこと．
